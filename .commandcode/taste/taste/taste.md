# Taste
- Backend local dev setup: PostgreSQL runs locally via `backend/docker-compose.yml` (container `oluora`); Alembic migrations are run from the backend venv (Python 3.14, `source venv/bin/activate && alembic upgrade head` in `backend/`); docker commands on this machine require sudo. Confidence: 0.7
- Keeps task specs and platform/API reference material as markdown files inside the repo (e.g. a per-task spec file plus `docs/references.md`) and expects the agent to read and rely on those files for links and API knowledge. Confidence: 0.6
- Explicitly invites the agent to ask clarifying questions before/while working rather than guessing. Confidence: 0.5
- Reports bugs by pasting raw error output (browser console/stack dumps, terminal/CLI errors like a `uvicorn` "Address already in use" traceback, and deploy-platform build/pre-deploy logs like a Render `alembic upgrade head` traceback) rather than describing the visible error or asking a question — expect noise (ad-blocker blocks, telemetry 4xx) to be filtered out and the real cause verified server-side/before answering. Confidence: 0.75
- Expects the agent to not make unsolicited "improvements" that alter existing behavior; reverts changes that break functionality (e.g., asked to restore the `youtube.force-ssl` scope the agent had removed). Do not strip features/scopes based on assumptions — verify against real behavior first. Confidence: 0.4
- Prefers a discussion/planning pass (options, trade-offs, recommendation) before implementation starts — frames new work as "let's discuss" rather than asking for immediate code. Confidence: 0.6
- Once options and trade-offs are laid out, is comfortable delegating the final technical/architecture decision to the agent ("make the call") and expects the reasoning and a concrete plan to be provided. Confidence: 0.5
- Wants platform ToS compliance, API limitations, and per-use cost/unit economics explicitly weighed as part of any integration decision, not just technical feasibility. Confidence: 0.6
- Treats security as a first-class decision factor for new and internal surfaces — frames requests by asking for the security approach up front and expects server-side enforcement, authorization, and hardening (not just client-side/UI guards) to be part of the plan. Confidence: 0.5
- Prefers third-party integrations to be vendor-agnostic/swappable (provider as a config value) rather than locked to one vendor — questions hardwired vendor choices ("do we have to use X?") and expects to be able to name an alternative provider. Confidence: 0.5
- Expects thorough, verified root-cause diagnosis: explicitly asks to "diagnose thoroughly" and pushes back when a proposed fix fails, so inspect the real current state (config, running processes, network/CORS behavior) and prove a fix works rather than offering speculative guesses. Confidence: 0.5
- For dev-environment resets, prefers wiping data only (`TRUNCATE ... RESTART IDENTITY CASCADE` on all tables) while preserving schema and Alembic migration state, rather than dropping/recreating the DB or debugging around stale rows. Confidence: 0.55
- When offered a trade-off on a security-sensitive surface, picks genuine isolation over the lower-effort shared option even at extra setup cost (e.g. chose a separate deployable app / separate origin for the admin dashboard over a same-app route group "for speed"). Confidence: 0.45
- Sometimes wants explanation-only responses when diagnosing an error — explicitly says "just explain, don't code" and expects a walkthrough of the likely causes and a checklist to fix, with no file edits or commands run. Confidence: 0.5
